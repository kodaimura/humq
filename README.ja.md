# HUMQ - カオスを設計するアーキテクチャ

<img align="right" src="assets/logo.png" alt="HUMQ logo" width="190">

**Language:** 日本語 | [English](README.md)

> **バグは直せる。歪みは、やがて手に負えなくなる。**

HUMQは、構造の歪みを許容しないアプリケーションアーキテクチャです。

「歪み」とは、責務境界が曖昧になり、<br>
処理の置き場所を構造から判断できなくなることです。

現実の業務では、当初の設計に収まらない分岐や特例が生まれます。<br>
そうしたカオスの置き場所が決まっていないと、構造は歪み始めます。<br>
HUMQは、そうしたカオスを排除して、すべてを秩序化しようとはしません。<br>
秩序の中に必要なカオスを許し、その置き場所と影響範囲を責務境界によって限定します。

> **どこに書くかを、人ではなく構造が決める。**

## 構造が歪んでいく例

注文確定は、注文を保存し、在庫を減らし、通知を送る単純なフローから始まります。<br>
運用が始まると、当初の設計に収まらない要求が加わります。

- 「旧契約の顧客だけは以前の価格を使う」
- 「サポート担当者は管理画面から確定済みの注文を取り消せる」
- 「月末の繁忙期だけは、通常と異なる承認経路を使う」
- 「データ移行から作られた注文には通知を送らない」

いずれも必要な要求ですが、処理の置き場所が決まっていなければ、<br>
実装者はその場で合理的な判断軸を選びます。

- 「管理画面だけの処理だから、Controllerに置く」
- 「注文状態のルールだから、Modelに置く」
- 「複数の処理をまたぐから、Serviceに置く」

どの判断も、その時点では間違いではありません。<br>
しかし、一度の特例的な配置が次の前例となり、同じ業務フローが複数の層へ分散します。<br>
コードが動いていても、正しい置き場所を説明できなければ、構造はすでに歪んでいます。

## 既存設計で構造が歪む理由

MVC + Service、Aggregate中心のDDD、Clean Architectureは、いずれも広く使われるアプリケーション設計のアプローチです。<br>
ただし、一部の責務境界は人の設計判断に委ねられます。

歪みは、間違った判断だけでなく、複数の合理的な判断が混在することで生まれます。

### MVC + Service

MVC + Serviceは責務を分離しますが、業務ロジックの置き場所を一意に定めません。

```text
Controller  -> このエンドポイント固有の処理だから
Model       -> このデータに関するルールだから
Service     -> 業務ロジックだから
```

どの配置も合理的であるため、判断が混在すると業務ロジックが複数の層へ分散します。

### Aggregate中心のDDD

Aggregate中心のDDDは、不変条件と振る舞いをDomainへ集約し、不正な状態を作りにくくします。<br>
一方で、AggregateやDomain Serviceの境界は業務概念から設計するため、<br>
チームで同じモデルと配置判断を維持し続ける必要があります。

### Clean Architecture

Clean Architectureは依存の方向を定め、業務ルールをFrameworkやDBから分離します。<br>
一方で、個々のルールをEntityとUsecaseのどちらに置くかや、Usecaseの粒度は設計判断に残ります。<br>
依存関係が正しくても、その判断が分かれれば処理の置き場所は実装者によって変わります。

HUMQは、これらの設計を否定しません。<br>
RDB中心のアプリケーションにおいて、人に委ねられる配置判断の一部を機械的な責務境界へ置き換え、<br>
人が変わっても置き場所が変わらない構造を目指します。

## HUMQの解決

HUMQは、外部との入出力をHandler、業務フローをUsecase、<br>
1テーブルの操作をModule、横断的な読み取りをQueryへ固定します。<br>
カオスを引き受ける場所を限定し、それ以外の責務境界を単純で予測可能に保ちます。

## 適用対象

主な対象は、RDBを主要な永続化基盤とし、複数テーブルの状態変更と横断的な読み取りを扱うアプリケーションです。<br>
向いている場面、引き受けるトレードオフ、別の設計が適する場面は、[適用判断とトレードオフ](docs/05-comparison.ja.md#適用判断とトレードオフ)で説明します。
