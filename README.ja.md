# HUMQ - カオスを設計するアーキテクチャ

<img align="right" src="assets/logo.png" alt="HUMQ logo" width="190">

**Language:** 日本語 | [English](README.md)

HUMQは、RDB中心のアプリケーションにおいて、呼び出し元との入出力をHandler、<br>
業務フローとトランザクションをUsecase、原則として1テーブルの読み書きをModule、<br>
複数テーブルを横断する読み取りをQueryへ固定するアプリケーションアーキテクチャです。<br>
主要な業務フローをUsecaseに残し、業務上の判断や状態変更の詳細は、<br>
明確な名前を持つ処理としてUsecaseから追跡できるようにします。

> **バグは直せる。歪みは、やがて手に負えなくなる。**

現実の業務では、当初の設計に収まらない分岐や特例が生まれます。<br>
HUMQでは、こうした業務上の複雑さを「カオス」と呼びます。

カオスの置き場所が決まっていないと、責務境界が曖昧になり、構造は歪み始めます。<br>
このように、複雑さの置き場所が崩れた状態が「歪み」です。

HUMQはカオスを排除しません。秩序の中に必要なカオスを許し、<br>
その置き場所と影響範囲を責務境界によって限定することで、構造の歪みを防ぎます。

> **構造で配置判断を減らし、処理の所在を予測しやすくする。**

## 構造が歪んでいく例

注文確定は、注文を保存し、在庫を減らし、通知を送る単純なフローから始まります。<br>
運用が始まると、当初の設計に収まらない要求が加わります。

- 「旧契約の顧客だけは以前の価格を使う」
- 「サポート担当者は管理画面から確定済みの注文を取り消せる」
- 「月末の繁忙期だけは、通常と異なる承認経路を使う」
- 「データ移行から作られた注文には通知を送らない」

いずれも必要な要求ですが、処理の置き場所が決まっていなければ、<br>
実装者はその場で合理的な判断軸を選びます。

- 「管理画面だけの処理だから、Controllerに置く」
- 「注文状態のルールだから、Modelに置く」
- 「複数の処理をまたぐから、Serviceに置く」

どの判断も、その時点では間違いではありません。<br>
しかし、一度の特例的な配置が次の前例となり、同じ業務フローが複数の層へ分散します。<br>
コードが動いていても、正しい置き場所を説明できなければ、構造はすでに歪んでいます。

## 既存設計で構造が歪む理由

MVC + Service、Aggregate中心のDDD、Clean Architectureは、<br>
いずれも広く使われるアプリケーション設計のアプローチです。<br>
ただし、一部の責務境界は人の設計判断に委ねられます。

歪みは、間違った判断だけでなく、複数の合理的な判断が混在することで生まれます。

### MVC + Service

MVC + Serviceは責務を分離します。チームがその構成の中で、業務ロジック、依存関係、<br>
トランザクションに明確な規約を設けることもできます。

例えば、「管理画面から確定済みの注文を取り消す」という同じ要求でも、<br>
実装者が重視する側面によって判断が変わります。

- 管理画面だけの処理なので、Controllerに置く。
- 注文状態を変更するルールなので、Modelに置く。
- 在庫の返却や通知も伴うので、Serviceに置く。

どの判断にも理由があります。<br>
こうした規約がなければ、MVC + Serviceだけではどの側面を配置基準として優先するかは決まりません。<br>
実装者ごとに異なる基準が選ばれると、同じ業務フローが複数の層へ分散し得ます。

### Aggregate中心のDDD

Aggregate中心のDDDは、不変条件と振る舞いをDomainへ集約し、不正な状態を作りにくくします。<br>
一方で、AggregateやDomain Serviceの境界は業務概念から設計するため、<br>
チームで同じモデルと配置判断を維持し続ける必要があります。

### Clean Architecture

Clean Architectureは依存の方向を定め、業務ルールをフレームワークやDBから分離します。<br>
一方で、個々のルールをEntityとUsecaseのどちらに置くかや、Usecaseの粒度は設計判断に残ります。<br>
依存関係が正しくても、その判断が分かれれば処理の置き場所は実装者によって変わります。

HUMQは、これらの設計を否定しません。<br>
RDB中心のアプリケーションにおいて、明確な責務境界で配置判断を減らし、<br>
処理の所在を予測しやすくします。Usecaseの粒度、ModuleとQueryの境界、<br>
内部処理の抽出には、引き続き設計判断が必要です。

## HUMQの解決

HUMQは、RDB中心のアプリケーションで、<br>
コードの置き場所に関する判断を減らすための軽量なアーキテクチャです。

Handler、Usecase、Module、Queryの責務境界を固定し、業務が複雑になっても、<br>
どこに何を書き、どこを追えばよいかを予測できる構造をつくります。<br>
独立して説明・検証・変更する意味がある業務処理は、使用箇所が1つでも、<br>
たとえば所有領域のUsecaseディレクトリ内で、明確な名前のファイルに切り出せます。<br>
切り出し自体は任意で、業務判断をUsecaseファイルに置いたままでも構いません。<br>
業務ルールを切り出す場合は`usecases/<domain>/_policies.py`を初期案として推奨します。<br>
横断的なルールの配置は、責任の所在と追跡しやすさを保てる形で利用側が選べます。<br>
処理の目的、主要な順序、結果による分岐、トランザクション境界、外部I/Oと失敗時の方針はUsecaseに残します。<br>
DBを使う内部処理は呼び出し元Usecaseと同じSessionに参加し、トランザクション境界を所有しません。<br>
カオスを引き受ける場所を限定し、それ以外の構造を単純で予測可能に保ちます。

MVC + Service単体より多くの配置境界を固定し、Aggregateや豊かなDomain Modelを中心とするDDDよりも、<br>
少ない設計概念で導入できます。

その軽量さと引き換えに、複数テーブルの整合性は各Usecaseが明示的に守ります。<br>
すべての領域をAggregateで保護するのではなく、<br>
構造的な保護が必要な領域を例外として扱う設計です。

## 適用対象

主な対象は、RDBを主要な永続化基盤とし、<br>
複数テーブルの状態変更と横断的な読み取りを扱うアプリケーションです。<br>
HUMQのメリットとデメリット、向いている場面、別の設計が適する場面は、<br>
[適用判断とトレードオフ](docs/05-comparison.ja.md#適用判断とトレードオフ)で説明します。
