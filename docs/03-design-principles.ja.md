# 設計原則

HUMQは、業務の本質的な複雑さを消そうとしません。下位の部品を単純に保ち、その組み合わせとして複雑さを追跡できるようにする設計です。

## 原則1: 重要な複雑さは隠さない

業務上意味のある処理順序、分岐、状態遷移、複数テーブル更新、外部I/O、トランザクション境界はUsecaseから見えるようにします。

一方、ORMの操作方法、SQLの組み立て、通信プロトコル、局所的なデータ変換は実装詳細として隠せます。HUMQが否定するのはカプセル化ではなく、業務フローを短く見せるためのカプセル化です。

```text
実装詳細は隠してよい。
業務フローは隠さない。
```

## 原則2: 局所的な複雑さを、隠れた複雑さより優先する

重要なのはコード量ではなく、1つの業務処理を理解するために何箇所を追う必要があるかです。

複数のServiceへ処理を分散した100行より、上から下まで読めばフローを理解できる300行のUsecaseの方が望ましい場合があります。ただし、これは巨大関数を無条件に認めるという意味ではありません。

**許容されるUsecase**

- 1つの説明可能な業務意志を表している
- 重要な手順、分岐、I/O、トランザクション境界を追える
- 呼び出すModule、Query、外部clientの役割が明確である

**見直すべきUsecase**

- 無関係な複数の業務意志が混ざっている
- 深いネストや共有可変状態によって順序を追えない
- Moduleが持つべき1テーブルの局所処理まで抱えている
- 抽出した補助処理の内部に業務フローが隠れている

## 原則3: Moduleには機械的な境界を与える

Moduleは正確に1テーブルだけを所有する、小さく予測可能な操作単位です。Aggregateや大きなDomain概念を表すものではなく、他のModuleも業務フローも知りません。

「関連するテーブル」を境界にすると、関連の範囲や例外を毎回判断する必要があります。HUMQはその設計判断自体を減らすため、1 tableという機械的で曖昧さのない境界を採用します。

```text
UserModule       -> users
OrderModule      -> orders
OrderItemModule  -> order_items
```

1つの業務概念が複数テーブルから構成されても構いません。その業務上のまとまりはUsecaseが表現します。ORM cascadeやhookなどによって別テーブルを暗黙に変更すると、この予測可能性が崩れるため避けます。

## 原則4: 業務フローは明示的に合成する

複数テーブルにまたがる操作は、各Moduleの呼び出しとしてUsecaseに並べます。

```text
CreateOrderUsecase
  OrderModule.create()
  OrderItemModule.createMany()
  InventoryModule.decrease()
  AuditLogModule.create()
```

Usecaseは、説明可能な1つの業務意志と主要なフローを1ファイルで示します。局所的な計算や純粋なPolicyは抽出できますが、複数Moduleの調整、外部I/O、状態遷移を補助Serviceへ隠してはいけません。

同じ業務判定を複数Usecaseで共有する場合も、判定の呼び出しと、その結果による分岐はUsecaseに残します。再利用と可視性は両立できます。

## 原則5: Queryは横断的な観測に徹する

1テーブルに閉じた読み取りはModuleに置きます。複数テーブルをまたぐ読み取りは、読み取り専用のQueryに置きます。

画面、検索、帳票の要求に合わせたJOINや集計を、書き込み境界であるModuleへ無理に閉じ込める必要はありません。ただしQueryは書き込まず、トランザクション境界も所有しません。

## 原則6: 整合性とSide Effectを隠さない

どのModuleをどの順序で組み合わせ、どの範囲を成功または失敗として扱うかはUsecaseに書きます。外部Side Effectも、発生箇所と失敗時の方針がUsecaseから分かるようにします。

DDDのAggregateは、その境界内の不変条件を明確に守る有力な方法です。HUMQはそれを否定するのではなく、テーブル単位の部品とUsecase上の明示的な整合性を既定値として選びます。自動的な保護より追跡可能性を優先する、意図的なトレードオフです。

## 原則7: 壊れたら直せる。歪んだら直せない

ここでいう「壊れる」とは、一般的なバグや実装ミスによってシステムが期待どおりに動かなくなることです。バグを許容したり、欠陥を放置したりするという意味ではありません。原因となる実装を修正すれば、期待する動作に戻せます。

一方、ここでいう「歪む」とは、構造上の責務境界が人や状況によって変わることです。個々の機能が動いていても、正しい置き場所と修正範囲を判断できなくなります。HUMQは、バグが起きないことを保証するのではなく、バグの修正や特例への対応によって構造全体が歪まないことを優先します。

HandlerがDB操作を始める、Moduleが別Moduleを呼ぶ、Moduleが複数テーブルを書き換える、Queryが書き込む、業務フローが補助Serviceへ消える、といった状態は構造の歪みです。歪みが入ると、コードの置き場所が人によって変わり、変更の影響範囲を追えなくなります。

迷ったときは、次の問いで判断します。

| 問い | 置き場所 |
| --- | --- |
| 外界からの入力と出力の話か | Handler |
| 業務フロー、整合性、状態遷移、外部I/Oの話か | Usecase |
| 正確に1テーブルに閉じた操作か | Module |
| 複数テーブルを横断する読み取りか | Query |

> Keep the parts simple. Keep the important chaos visible.
