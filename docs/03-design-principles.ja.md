# 設計原則

HUMQは、すべてを綺麗に保つための設計ではありません。汚れてよい場所を明確にし、歪んではいけない場所を守るための設計です。

## 原則1: 壊れてもよい、歪むな

HUMQでは、壊れることと歪むことを区別します。

| 観点 | 壊れる | 歪む |
| --- | --- | --- |
| 原因 | 実装ミス、仕様変更、一時的な欠損 | 責務逸脱、層の混在、概念の崩壊 |
| 修復性 | 修正できる | 修正が難しい |
| HUMQでの扱い | 局所的なカオスとして許容する | 構造の破壊として避ける |
| 主な修復場所 | Usecase | 構造全体 |

Usecaseの中で業務要件が複雑になることはあります。それは現実のカオスを引き受けている状態です。

一方で、HandlerがDB操作を始める、Moduleが他Moduleを呼び始める、Moduleが複数テーブルを抱える、Queryが書き込みを始める、業務フローがModuleへ漏れる、といった状態は歪みです。歪みは一度入ると、コードの置き場所が人によって変わり、秩序が失われます。

## 原則2: 自由を設計する

自由を完全に禁止すると、逸脱は別の場所に漏れます。HUMQでは、Usecaseを自由の場所として設計します。

Usecaseは次のものを引き受けます。

- 業務の例外
- 一時的な仕様
- 複雑な分岐
- 複数Moduleの組み合わせ
- 整合性の明示的な制御

カオスは許します。しかし、何をしてもよいわけではありません。Usecaseは複雑になっても構いませんが、その複雑さは説明可能な1つの業務意志としてまとまっている必要があります。

Usecaseの自由は、無関係な業務処理を1つの巨大Usecaseに詰め込む理由にはなりません。同じ業務処理が複数Usecaseで重複する場合は、責務を見極めて適切に抽出します。ただし、Usecaseを綺麗に見せるためだけに業務ロジックをModuleへ押し込んではいけません。

この自由があるから、Handler、Module、Queryは比較的純粋に保てます。これが「壊れてもよい、歪むな」とつながります。Usecaseは変更され、修復されてもよい。その間も構造の境界は安定させます。

## 原則3: Moduleは世界の法則として扱う

Moduleは、アプリケーション内部の安定した局所的なテーブル秩序です。

Moduleは正確に1テーブルに閉じます。Aggregateや大きな業務上のSubjectを表現するものではありません。他のModuleを知りません。業務フローも知りません。Usecaseから呼ばれるための部品として、テーブル固有の操作を提供します。

Moduleに例外的な業務都合を入れると、Moduleは再利用しにくくなります。さらに、その例外を必要としないUsecaseから見ても不自然な振る舞いになります。

1つの業務処理が3テーブルにまたがる場合、HUMQでは1つの巨大なModuleではなく、3つのModuleを1つのUsecaseが組み合わせます。

## 原則4: Queryは観測に徹する

1テーブルに閉じた読み取りはModuleに置きます。複数テーブルをまたぐ読み取りは、Moduleに押し込めません。Moduleの秩序はテーブル単位であり、横断的な読み取りとは性質が違うためです。

Queryはこの横断性を受け入れるための層です。ただし、書き込みはしません。観測するだけです。

## 原則5: 整合性を隠さない

HUMQは、整合性をUsecaseで明示します。

DDDのAggregateのように整合性を内部に閉じる設計は、理論的には強力です。しかし実務では、業務操作がUsecaseに閉じていることも多く、整合性を閉じ込めるほど再利用性が落ちる場合があります。

HUMQでは、どのModuleを組み合わせて整合性を保つのかをUsecaseに書きます。これは自動的な安全性を捨てる代わりに、構造の見通しと変更しやすさを得る選択です。

## 原則6: 責務境界を最優先する

HUMQで最も重要なのは、各層の責務が揺れないことです。

便利だからという理由で境界を越えると、短期的には速くても、長期的には置き場所の基準が失われます。

迷ったときは、次の問いで判断します。

| 問い | 置き場所 |
| --- | --- |
| 外界からの入力と出力の話か | Handler |
| 業務フローや整合性の話か | Usecase |
| 正確に1テーブルに閉じた操作か | Module |
| 複数テーブルを横断する読み取りか | Query |
