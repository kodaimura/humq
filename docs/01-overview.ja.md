# HUMQの概要

HUMQは、既存アーキテクチャで曖昧になりがちな責務を、Handler / Usecase / Module / Query という4つの実務ルールへ再定義するアーキテクチャです。

MVC、レイヤードアーキテクチャ、クリーンアーキテクチャ、DDDが抱えがちな「責務境界の曖昧さ」を避けるために、コードの置き場所を責務で分解します。HUMQの価値は、置き場所の判断が歪みにくくなる制約を設計することです。

## HUMQが解く問題

既存の設計では、次の迷いが起きやすくなります。

- Controllerにどこまで書いてよいのか。
- ServiceとRepositoryの境界はどこか。
- Domainに業務例外を入れるべきか。
- 複数テーブルをまたぐ読み取りはどこに置くべきか。
- トランザクションは誰が管理するべきか。

HUMQはこの迷いを、責務を実務向けのルールとして再定義することで減らします。

## 基本思想

HUMQの中心にあるのは、秩序とカオスの分離です。

- 秩序を守る場所を決める。
- カオスを受け入れる場所を決める。
- 複数テーブルを横断する観測を読み取り専用として隔離する。
- 整合性は隠さず、Usecaseで明示する。

HUMQは「壊れない設計」ではありません。現実の仕様変更や例外によって壊れることはあります。ただし、壊れる場所がUsecaseへ寄るため、片付ける範囲が限定されます。

## 4つのルールの全体像

| 層 | 世界観 | ファイル命名 | トランザクション境界を所有するか | 書き込み |
| --- | --- | --- | --- | --- |
| Handler | 外界の秩序 | 複数形の名詞 | 持たない | 直接しない |
| Usecase | 意志、業務単位 | 動詞 | 持つ | Moduleを通じて行う |
| Module | 局所的なテーブル秩序 | 単数形のテーブル名 | 持たない | ORMなどを使った1テーブルの読み書き |
| Query | 観測、構造的カオス | 業務文脈名 | 持たない | しない |

## 依存の考え方

HUMQでは、基本的に次の流れで処理します。

```text
Single-table operation:
Handler -> Usecase -> Module

Cross-table read:
Handler -> Usecase -> Query
```

HandlerはUsecaseを呼びます。Usecaseは必要なModuleやQueryを組み合わせます。ModuleはORMなどの永続化手段を使い、正確に1テーブルに閉じた読み書きを提供します。

複数テーブルを横断する画面、レポート、検索エンドポイントでは、UsecaseがQueryを呼びます。Queryは複数テーブルの読み取りや集計を担当しますが、書き込みはせず、トランザクション境界も所有しません。

重要なのは、Module同士を直接依存させないことです。複数のModuleを組み合わせる必要がある場合、その責務はUsecaseにあります。

## HUMQで守るもの

HUMQが守るのは完全な整合性ではなく、説明可能な秩序です。

整合性をすべてDomainやAggregateに閉じ込めるのではなく、Usecaseに出します。どのModuleをどの順序で組み合わせ、どの範囲をトランザクションとして扱うのかを、コード上で見えるようにします。

その代わり、設計者と実装者はUsecaseに責任を持つ必要があります。Usecaseは自由な層ですが、無秩序にしてよい層ではありません。Usecaseは複雑になっても構いませんが、その複雑さは説明可能な1つの業務意志としてまとまっている必要があります。
