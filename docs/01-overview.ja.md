# HUMQの概要

HUMQは、重要な複雑さを隠さず、単純で予測可能な部品の組み合わせとして業務フローを表現するアーキテクチャです。

Handler / Usecase / Module / Queryという4つの責務と機械的な境界によって、コードの置き場所と、複雑さを表現する場所を固定します。HUMQの価値は、抽象化の数を減らすことではなく、処理を追跡するための間接参照と、置き場所を決めるための設計判断を減らすことです。

## HUMQが解く問題

既存の設計では、次の迷いが起きやすくなります。

- Controllerにどこまで書いてよいのか。
- ServiceとRepositoryの境界はどこか。
- Domainに業務例外を入れるべきか。
- 複数テーブルをまたぐ読み取りはどこに置くべきか。
- トランザクションは誰が管理するべきか。

HUMQはこの迷いを、責務を実務向けのルールとして再定義することで減らします。

## 中心思想

> **重要な複雑さは隠さない。**

業務そのものが複雑なら、その複雑さはコード上にも現れて構いません。HUMQは、ServiceやRepositoryの内部へ業務手順を押し込み、呼び出し側だけを短く見せることを目的としません。

ただし、すべてをUsecaseへ露出するわけではありません。

| 隠してよいもの | Usecaseから見えるべきもの |
| --- | --- |
| ORMやSQLの組み立て | 複数テーブルに対する操作 |
| DBアクセス方法 | 業務上意味のある処理順序と分岐 |
| 局所的なデータ変換 | 状態遷移と整合性の判断 |
| 外部clientの通信手順 | 外部I/Oの発生と失敗時の扱い |
| 1テーブル操作の実装詳細 | トランザクション境界 |

実装詳細は隠してよい。業務フローは隠さない。これがHUMQにおけるカプセル化の立場です。

## 4つのルールの全体像

| 層 | 世界観 | ファイル命名 | トランザクション境界を所有するか | 書き込み |
| --- | --- | --- | --- | --- |
| Handler | 外界の秩序 | 複数形の名詞 | 持たない | 直接しない |
| Usecase | 意志、業務単位 | 動詞、1フロー1ファイル | 必要な境界を決める | Moduleを通じて行う |
| Module | 局所的なテーブル秩序 | 単数形のテーブル名 | 持たない | ORMなどを使った1テーブルの読み書き |
| Query | 観測、構造的カオス | 業務文脈名 | 持たない | しない |

## 依存の考え方

HUMQでは、基本的に次の流れで処理します。

```text
Handler
   │
   ▼
Usecase
   ├── Module          -> 1テーブルの読み取り / 書き込み
   ├── Module          -> 1テーブルの読み取り / 書き込み
   ├── Query           -> 複数テーブルを横断する読み取り
   └── External Client -> Side Effect
```

HandlerはUsecaseを呼びます。Usecaseは必要なModule、Query、外部clientを明示的に組み合わせます。ModuleはORMなどの永続化手段を使い、正確に1テーブルに閉じた読み書きを提供します。

複数テーブルを横断する画面、レポート、検索エンドポイントでは、UsecaseがQueryを呼びます。Queryは複数テーブルの読み取りや集計を担当しますが、書き込みはせず、トランザクション境界も所有しません。

重要なのは、Module同士を直接依存させず、業務上意味のある組み合わせをUsecaseから見える状態にすることです。複数のModule、外部I/O、状態遷移を束ねる責務はUsecaseにあります。

## HUMQで守るもの

HUMQが守るのは、すべてを自動的に安全にすることではなく、説明可能で追跡可能な秩序です。

整合性をすべてDomainやAggregateに閉じ込めるのではなく、Usecaseに出します。どのModuleをどの順序で組み合わせ、どの範囲をトランザクションとして扱うのかを、コード上で見えるようにします。

その代わり、設計者と実装者はUsecaseに責任を持つ必要があります。Usecaseは複雑になっても構いませんが、無関係な業務意志、深いネスト、追跡不能な状態変更まで許容するわけではありません。長さではなく、1つの業務意志として上から下まで説明できるかで判断します。

## 適用対象と設計上の前提

HUMQは、RDBを主要な永続化基盤とし、複数テーブルの状態変更と横断的な読み取りを扱うアプリケーションを主な対象とします。

HUMQのModule境界は、データベースのテーブル構造に意図的に結び付きます。これは、永続化から独立した豊かなDomain Modelを作ることより、操作対象の予測可能性と、境界を決める判断の少なさを優先する選択です。
