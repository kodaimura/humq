# 層と責務のルール

このドキュメントでは、HUMQの各層に置くもの、置かないもの、命名規則を定義します。

## Handler

Handlerは外界の入口です。HTTPリクエスト、イベント、CLI入力など、アプリケーション外部から来た入力を受け取り、Usecaseへ渡します。

### 置くもの

- ルーティング
- リクエストの受け取り
- レスポンスの整形
- 入出力スキーマとの接続
- 認証済みユーザーなど、外界から得た文脈の受け渡し

### 置かないもの

- 業務ロジック
- DB操作
- トランザクション管理
- 複数Moduleの組み合わせ
- 集計やJOINの組み立て

### 命名

Handlerのファイル名はURLリソースに合わせ、複数形の名詞にします。

```text
handlers/
├── accounts.py
├── projects.py
├── users.py
└── health.py
```

## Usecase

Usecaseは説明可能な1つの業務意志を表す層です。複数のModuleを組み合わせ、現実の例外、分岐、整合性、トランザクションを引き受けます。

Usecaseの目的は、呼び出し側を短く見せることではありません。1つの業務処理について、重要な手順を1箇所で追えるようにすることです。

### 置くもの

- 業務フロー
- 条件分岐
- 複数Moduleの組み合わせ
- Queryの利用
- 業務フロー上必要なmailerや外部clientなどの呼び出し
- トランザクション境界
- 状態遷移と、外部Side Effectの失敗時の扱い
- 例外的な業務要件

### 置かないもの

- HTTPリクエストやレスポンスへの直接依存
- 生SQLによる横断的な読み取り
- ORMモデルへの直接依存
- `commit` / `rollback` をModuleへ委譲する設計
- Usecaseから別のUsecaseを呼び、主要な業務フローを隠す設計
- 一部のコードが似ているという理由で無関係な業務処理をまとめた巨大Usecase

### 1 Usecase = 1 Primary Flow

1つのUsecaseは、説明可能な1つの業務意志と、その主要なフローを1ファイルで示します。少なくとも次の情報は、そのUsecaseファイルから読み取れなければなりません。

- 業務上意味のある処理の順序
- 重要な条件分岐
- どのModuleとQueryを使うか
- 外部I/Oがどこで発生するか
- 状態変更とトランザクションの境界

Usecaseが長いこと自体は問題ではありません。複数のServiceへ処理を分散した100行より、上から下まで読めば1つの業務フローを理解できる300行の方が望ましい場合があります。

ただし、長さは無秩序を許す理由にはなりません。無関係な業務意志が混ざる、深いネストで順序が追えない、共有可変状態が増え続ける場合は、Usecaseの境界または表現を見直します。

### 補助処理と共有ルール

局所的な計算、データ変換、フォーマット処理は、業務フローを隠さない範囲で関数や補助ファイルへ抽出できます。

複数Usecaseで同じ業務判定が必要な場合は、純粋なPolicyや判定関数として共有できます。ただし、その補助処理はModule、Query、外部clientを呼ばず、トランザクションを所有しません。Policyを呼ぶことと、その結果による分岐はUsecaseに明示します。

補助処理は新しいService層ではありません。複数のModuleや外部I/Oを束ねる処理を補助ファイルへ移すと、業務フローが再び隠れるためです。

### 命名

UsecaseのディレクトリはHandlerと同じく複数形のリソース名にします。各Usecaseファイルは動詞または動詞句にします。

```text
usecases/
├── accounts/
│   ├── signup.py
│   ├── login.py
│   ├── update_profile.py
│   └── delete.py
└── projects/
    ├── create.py
    └── archive.py
```

`usecases/accounts/signup.py` は、ディレクトリが文脈を語るため十分です。`register_user.py` のように対象を重ねる命名は避けます。公開されるUsecaseの入口も1つにし、そのファイルを読めば主要なフローを追える状態にします。

## Module

Moduleは、正確に1テーブルに閉じます。

ModuleはBusiness Usecase、Aggregate、大きな業務上のSubjectを表現するものではありません。小さく安定した、局所的なテーブル秩序です。1つの業務処理が3テーブルにまたがる場合、HUMQでは1つの巨大なModuleではなく、3つのModuleを1つのUsecaseが組み合わせます。

この制約は、関連性やAggregate境界を毎回判断せず、Module名から操作対象を予測できるようにするためのものです。Module同士は直接呼び出しません。複数テーブルにまたがる業務フローはUsecaseの責務です。

HUMQが管理する各書き込み対象テーブルには、書き込みを所有するModuleを1つだけ対応させます。Queryはそのテーブルを読み取れますが、別のModuleが同じテーブルの書き込みAPIを持つことはできません。中間テーブルも書き込み対象であれば、独立したModuleを持ちます。

### 置くもの

- 1テーブルに閉じた取得、作成、更新、削除
- Usecaseから使われる単純な1テーブル検索
- テーブル固有の不変条件
- ORMなどを使った意味のある操作

### 置かないもの

- 複数Moduleをまたぐ業務フロー
- 複数テーブルにまたがる操作
- Usecaseの都合による一時的な条件分岐
- Usecaseを綺麗に見せるためだけに切り出した業務ロジック
- トランザクション管理
- 他Moduleへの直接依存
- JOINや集計を中心にした読み取り
- mailer、payment gateway、API client など、テーブルに対応しない外部連携
- ORM relationのlazy loadなどによる、別テーブルへの暗黙の読み取り
- ORM cascade、event hook、callbackを使った、別テーブルへの暗黙の書き込み

Moduleの操作から、別のアプリケーションテーブルが暗黙に変更されてはいけません。DB triggerや参照cascadeが避けられない場合は、その挙動をUsecaseから追跡できるように明記し、HUMQの通常規則に対するアーキテクチャ上の例外として管理します。

### 命名

Module名は、1テーブルに対応する単数形の名詞にします。

```text
modules/
├── account/
│   ├── model.py
│   └── module.py
├── project/
│   ├── model.py
│   └── module.py
└── account_role/
    ├── model.py
    └── module.py
```

テーブルを持たない関心事は、`modules/` 配下には置きません。ViewやMaterialized Viewは書き込みを所有するModuleではなく、読み取り専用のQueryとして扱います。

### Repositoryについて

RepositoryはHUMQの必須要素ではありません。ModuleがORMを直接扱ってよいです。

同じ1テーブルへの永続化処理が増えすぎる場合や、ORMを使わないアクセス実装を分離したい場合だけ、Module内部の補助ファイルとして`repository.py`を切り出します。その場合でもRepositoryは外部公開する層ではなく、Usecaseから直接呼びません。Repositoryを切り出しても、Moduleの操作対象が1テーブルであることは変わりません。

## Query

Queryは複数テーブルを横断する読み取りのための、読み取り専用の観測ルールです。JOIN、集計、レポート、一覧表示のための横断的な読み取りを担当します。

1テーブルに閉じた読み取りは、検索や集計が複雑でもModuleに置きます。Queryは、複数テーブルを観測することで意味が生まれる読み取りや、複数テーブルにまたがるレポート・検索文脈のために存在します。

Queryはトランザクション境界を所有しません。`commit` や `rollback` は呼びません。利用しているORMやDB接続の内部でトランザクションが存在するかどうかは、別の実装詳細です。

### 置くもの

- JOIN
- 集計
- レポート取得
- 検索画面用の読み取り
- 複数Moduleを横断する読み取り

### 置かないもの

- 書き込み
- トランザクション管理
- 業務状態の変更
- Moduleの代わりになるCRUD

### 命名

Queryはエンティティ名ではなく、観測対象や業務文脈で命名します。

| 観測対象 | ファイル名 |
| --- | --- |
| アカウントの注文履歴 | `account_orders.py` |
| プロジェクト進行状況 | `project_progress.py` |
| 売上集計 | `sales_report.py` |
| ユーザー行動全体 | `activity_overview.py` |

Queryは「どのテーブルか」ではなく「何を観測しているか」を語る層です。
