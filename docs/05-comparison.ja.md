# 既存アーキテクチャ・設計パターンとの比較

HUMQは、MVC + Serviceよりコードの置き場所を明確にし、<br>
Aggregate中心のDDDより少ない設計概念で導入できる、軽量なアプリケーションアーキテクチャです。<br>
その代わり、複数テーブルの整合性をDomain Modelで構造的に守らず、各Usecaseの実装に委ねます。

このページでは、HUMQがなぜこのトレードオフを選ぶのか、<br>
どのようなアプリケーションに向き、どの時点で別の設計を選ぶべきかを説明します。

MVC、レイヤードアーキテクチャ、Clean Architecture、DDD、Transaction Script、<br>
Table Module、CQRSは、同じ階層の概念ではありません。<br>
複数を併用できる場合もあれば、設計上の優先順位が衝突する組み合わせもあります。<br>
ここでは、各設計を典型的な形で採用した場合の、配置、追跡可能性、<br>
整合性の保証、RDBとの結合に関する既定値を比較します。

## 比較の観点

個別の設計は、次の4つの観点で比較します。

- 何をアーキテクチャによって守るか。
- 業務フローと複雑さをどこへ置くか。
- 責務境界のうち、どこまでを人の設計判断に残すか。
- RDBのテーブル構造と、どの程度結合するか。

以下では、各アーキテクチャについて、特に違いが現れる観点を中心に比較します。

## HUMQの位置付け

| 設計 | 主に最適化するもの | 境界の基準 | 主なトレードオフ |
| --- | --- | --- | --- |
| MVC + Service | 関心の分離と<br>構成の柔軟性 | Controller、Model、Serviceなど、<br>チームが定める役割 | 同じ処理に複数の合理的な<br>置き場所が生まれやすい |
| HUMQ | 配置の予測可能性と<br>業務フローの追跡可能性 | Usecaseのフロー、原則として1テーブル単位のModule、<br>複数テーブルを横断するQuery | 複数テーブルの整合性を<br>Usecaseの実装が担う |
| Aggregate中心のDDD | Domain Modelによる不変条件と<br>業務概念の保護 | Bounded Context、Aggregate、<br>Entity、Value Objectなど | 継続的なモデリングと、<br>境界を共有する設計判断が必要になる |

HUMQは、MVC + ServiceとDDDの中間段階でも、<br>
設計の成熟度を表す上位・下位でもありません。何を構造で守るかについて、異なる既定値を選びます。<br>
HUMQからAggregate中心のDDDへ移ることは設計のアップグレードではなく、<br>
配置と追跡可能性よりも、不変条件の構造的な保護を優先するという最適化対象の変更です。

HUMQはAggregate、Value Object、Domain Service、Repository、<br>
Bounded Contextを必須としません。ORMモデルとRDBテーブルへの結合を許容し、<br>
ドメインモデリングより配置の予測可能性と業務フローの追跡可能性を優先します。

## 同じ業務フローで見る違い

例えば注文確定では、注文明細の金額を確定し、その合計を注文金額へ反映して、<br>
注文の状態を確定済みにする必要があるとします。

- **MVC + Service**では、処理をController、Model、Serviceのどこで組み合わせるかをチームが決めます。<br>
  構成を柔軟に選べますが、実装者によって配置判断が分かれる可能性があります。
- **HUMQ**では、`ConfirmOrderUsecase`が`OrderItemModule`と`OrderModule`を明示的に呼び出します。<br>
  変更時に追う場所は明確ですが、<br>
  必要なModuleを呼び忘れると、整合性ルールの実装漏れが起こり得ます。
- **Aggregate中心のDDD**では、注文と注文明細の不変条件をOrder Aggregateへ閉じ込め、<br>
  不正な更新を作りにくくします。その代わり、Aggregateの境界を設計し、<br>
  モデルと実装を継続的に一致させる必要があります。
- **Transaction Script**では、注文確定を1つの手続きとして記述し、処理を上から下へ追えます。<br>
  ただし、データアクセスや横断的な読み取りをどこへ置くかまでは決まりません。

違いは、業務処理を実装できるかではありません。<br>
MVC + Serviceは構成の柔軟性、Transaction Scriptは手続きとしての追跡可能性、<br>
HUMQは追跡可能性と配置の一貫性、Aggregate中心のDDDは不変条件の構造的な保護を優先します。

## MVC + Service / レイヤードアーキテクチャ

MVC + Serviceやレイヤードアーキテクチャは、入出力、業務処理、データアクセスを分離します。<br>
広く理解されており、システムの規模や特性に合わせて層の粒度を調整できる柔軟な設計です。

一方で、Serviceの粒度、Modelに持たせる振る舞い、Repositoryの責務、<br>
トランザクションの所有者はチームが決めます。<br>
同じ処理でも、Controller、Model、Serviceのどこに置くかについて複数の合理的な判断が成り立ちます。

HUMQは汎用的なServiceを置かず、呼び出し元との入出力をHandler、業務フローをUsecase、<br>
原則として1テーブルの読み書きをModule、複数テーブルを横断する読み取りをQueryへ固定します。<br>
柔軟性を減らす代わりに、処理の置き場所が実装者によって変わることを防ぎます。

HUMQの価値は新しい概念を発明することではなく、<br>
既存の実装パターンから必要最小限を選び、配置判断を減らすことにあります。

## Clean Architecture

Clean Architectureは依存の方向を制御し、<br>
業務ルールをフレームワークやDBなどの外部詳細から独立させます。<br>
技術要素を交換しやすくし、重要な方針を内側に守ることに強みがあります。

ただし、個々のルールをEntityとUsecaseのどちらに置くか、<br>
UsecaseやPortをどの粒度にするかは設計判断に残ります。<br>
依存関係が正しくても、処理の置き場所が一意に決まるとは限りません。

HUMQが追加で固定するのは、操作対象と処理の置き場所です。<br>
Clean Architectureは、DomainやUsecaseをORM、Webフレームワーク、<br>
DBなどから独立させることを重視します。HUMQはその独立を必須とせず、<br>
UsecaseがSessionやORMモデルを扱うことを許容します。

HUMQはDBテーブルをModuleの境界とするため、<br>
DBスキーマの変更がModuleの境界や命名にも影響します。技術要素の交換可能性よりも、<br>
コードの置き場所と業務フローの追跡可能性を優先する点が、両者の大きな違いです。

## Aggregate中心のDDD

Aggregate中心のDDDは、業務概念、不変条件、状態遷移をDomain Modelへ集約し、<br>
不正な状態を作りにくくします。<br>
複雑な整合性ルールをモデル自身に守らせることに強みがあります。

一方で、Aggregate、Entity、Value Object、Domain Serviceの境界は、<br>
業務を継続的にモデリングして決めます。<br>
Aggregateをまたぐ処理、横断的な画面要求、暫定対応をどこへ置くかには、<br>
チームで共有された設計判断が必要です。

HUMQはDomainの境界ではなく、RDBのテーブルをModuleの境界にします。<br>
複数テーブルの整合性はUsecaseの実装に委ね、業務フローから追跡できる状態を保ちます。<br>
HUMQはDDDを簡略化したものではなく、<br>
モデリングによる保護よりも配置の予測可能性を優先する別の選択です。

すべての領域で最初から豊かなAggregateを設計すると、不変条件が単純な領域にも、<br>
モデルと境界を設計し続けるコストがかかります。HUMQは軽量な構造から始め、<br>
同じ不変条件を複数Usecaseで守る必要がある場合に限り、<br>
例外的にOperationへの集約を検討します。<br>
複雑な共有不変条件が領域の中心になる場合は、Aggregate中心の設計が適します。

## Transaction Script

Transaction Scriptは、1つの業務処理を1つの手続きとして表現します。<br>
業務フローを上から順に追えるため、HUMQのUsecaseに最も近いパターンです。

ただし、Transaction Script単体では、データアクセスの境界、横断的な読み取りの置き場所、<br>
トランザクション境界の表現方法まで統一されません。<br>
各ScriptがDBを直接操作するか、異なるGatewayやRepositoryを使い始めると、<br>
下位部品の責務や整合性の扱いが揃わないことがあります。

HUMQはTransaction Scriptに、`1 Usecase = 1つの主要フロー`、<br>
`Module = 原則として1テーブルの読み書き`、`Query = 複数テーブルを横断する読み取り`、<br>
`トランザクション境界をUsecaseに明示する`という機械的な境界を加えます。<br>
Usecaseの手続き的な性質を隠さず、下位部品だけを単純で予測可能に保ちます。

## Table Module / Table Data Gateway

Table Moduleは1テーブルまたはViewに関する業務ロジックを1つの部品へまとめ、<br>
Table Data Gatewayは1テーブルへのデータアクセスをまとめます。<br>
どちらも、RDBのテーブルを明示的な境界として扱う点でHUMQのModuleに近いパターンです。

ただし、これらのパターンだけでは、複数テーブルを使う業務フロー、<br>
横断的な読み取り、外部I/O、トランザクションをどこで組み合わせるかは決まりません。

HUMQのModuleは、原則として1テーブルの読み書きと標準操作を提供します。<br>
対象テーブルへの書き込みに必要な場合だけ、例外として別テーブルを参照できますが、<br>
別テーブルへの書き込み、業務フロー、トランザクション境界は持ちません。<br>
Table単位の部品に加えて、それらをUsecaseから組み合わせ、<br>
複数テーブルを横断する読み取りをQueryへ分けるところまでを、<br>
アーキテクチャの規則にします。

## CQRS

CQRSは、状態を変更するためのModelと、状態を読み取るためのModelを分離します。<br>
同じデータストアを共有する構成もあれば、異なるデータストアやProjectionを使う構成もあります。

HUMQのQueryも、用途に合ったRead Modelを構築する点では、<br>
CQRSのQuery側やRead側に近い責務です。複数テーブルの横断が基本ですが、<br>
Moduleの標準操作に収まらない複雑または用途固有の読み取りは、<br>
例外として1テーブルでもQueryに置けます。<br>
ただし、HUMQはすべての操作に独立したCommand ModelとRead Modelを要求しません。<br>
別データストア、非同期なProjection更新、結果整合性もHUMQの前提ではありません。

CQRSは読み取りと書き込みを分けますが、<br>
Command側の業務フローやデータアクセスをどの境界へ置くかまでは決めません。<br>
HUMQは、読み書きの分離に加えて、Handler、Usecase、Module、Queryの配置規則まで固定します。

## 適用判断とトレードオフ

ここまでの比較を、実際の採用判断に当てはめます。

HUMQは、RDBを主要な永続化基盤とし、<br>
複数テーブルの状態変更と、画面、検索、帳票などのための横断的な読み取りを扱う、<br>
アプリケーションを主な対象とします。

### HUMQが向いている場面

- 業務の状態を安定したRDBテーブルで管理している。
- 複数テーブルをまたぐ処理に、分岐、特例、暫定対応が増え続ける。
- 一覧、検索、帳票など、複数テーブルを横断する読み取りが多い。
- 複数人で長期運用し、コードの置き場所に関する判断を減らしたい。
- 同じ不変条件を多数の操作で共有するより、業務ルールの多くが個別のUsecaseに結び付いている。

HUMQを採用すると、業務フロー、状態遷移、トランザクション境界をUsecaseから追いやすくなり、<br>
1テーブル操作の影響範囲と、変更時に確認するコードを予測しやすくなります。<br>
副次的に、1つの変更を理解するために読む範囲が限定されるため、<br>
AIエージェントも変更対象を把握しやすくなります。

### HUMQを使う効果が小さい場面

- ほとんどの処理が1テーブルの単純なCRUDで完結する。
- 複数テーブルをまたぐ業務フローや読み取りがほとんどない。
- 少人数または短期開発で、処理の置き場所が問題になっていない。

この場合、HUMQを採用しても得られる予測可能性は少なく、<br>
より単純なMVCやレイヤードアーキテクチャで十分なことがあります。

### HUMQが引き受けるトレードオフ

- 業務フローと整合性の判断が集まるため、Usecaseが大きくなりやすい。
- Moduleをテーブル構造へ結合するため、DBスキーマの変更が境界や命名へ影響する。
- 正規化されたテーブル構造が、複数のModule呼び出しとしてUsecaseに現れる。
- 複数テーブルの整合性はUsecaseの実装に依存し、ルールの実装漏れが不整合につながる。

HUMQは、整合性が重要ではないと考えているのではありません。<br>
実際の多くのシステムでは、Aggregateによる構造的な保護が必要な領域は、<br>
少数に限られるという前提に立っています。<br>
その前提のもとで、整合性ルールの実装漏れが起こり得るリスクを、<br>
軽量で明確な配置規則を得るためのトレードオフとして意図的に引き受けます。

DB制約とテストはそのリスクを軽減しますが、実装漏れそのものを構造的には防ぎません。<br>
このリスクを許容できない場合は、要件を構造的に守る別の設計を選びます。

スキーマの複雑さがUsecaseに現れることは、HUMQが意図的に受け入れるトレードオフです。<br>
抽象的なDomain境界で隠すことより、「このテーブルを変更するコードはどこか」に、<br>
機械的に答えられることを優先します。

### 別の設計を選ぶ場面

| 中心となる要件 | 適する設計 |
| --- | --- |
| 同じドメインの複数テーブルを常に1つの単位として更新し、<br>複雑な不変条件を多数の操作で共有する | Aggregate中心のDDD |
| DomainをRDBや保存方式から<br>厳密に独立させる必要がある | Clean Architectureなど、<br>Domainを内側に置く設計 |
| イベント履歴が主要な永続化モデルになる | Event Sourcing |
| 複数の外部システムをまたぐ長時間の処理と、<br>再試行や補償の管理が中心になる | Workflow Engineなど |

### HUMQを採用するときに守ること

- Usecaseを、上から下まで説明できる1つの業務目的に保つ。
- 業務フロー、複数テーブルの整合性、トランザクション境界、外部I/OをUsecaseに明示する。
- Moduleを原則として1テーブルの読み書き、Queryを読み取り専用、Handlerを外部との入出力に限定する。
- DBで表現できる制約はDBで守り、Usecaseが担う整合性と`rollback`をテストする。
- Operationは、同じ不変条件の実装を分岐させられない場合だけに使う。

HUMQの機械的な境界は、業務上の正しさを自動では保証しません。<br>
正しさを実装し、確認する場所を固定します。
